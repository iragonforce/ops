# Homelab SSH routing

## When to Use

Use for client-to-host SSH reachability, LAN/Tailscale fallback, host-key trust, and SSH-agent/key migration across the homelab.

Read current AGENTS.md and context/01-hosts-and-access.md; historical LAN addresses may no longer match current DHCP/private-MAC clients. Distinguish Nexus Docker's routing from Nexus host routing.

- Inspect `ssh -G <alias>` on the actual originating machine, including Include ordering, hostkeyalias, identities and ProxyCommand. First obtained scalar settings generally win; do not assume a later Host stanza overrides earlier included settings.
- Verify direct LAN and tailnet transports with BatchMode, bounded timeout, ControlPath=none and strict existing host-key trust before changing anything. Do not expose keys or credentials.
- Compare current client source IP with the target's narrow firewall allowlist. Correlate a bounded TCP-header capture with drop-counter changes to establish a firewall cause without editing rules. A working Tailscale session does not imply raw-LAN authorization.
- Preserve an existing tailnet session and avoid router, firewall or service changes when a client-only repair suffices. Do not disable interfaces merely to test fallback.
- If this container cannot reach a host, inspect available trusted host paths before declaring the host inaccessible. In this environment an existing privileged node-exporter container mounts host /proc at /host/proc and supports nsenter; verify those facts live. Read-only host diagnostics can run via `docker exec node-exporter /bin/nsenter --mount=/host/proc/1/ns/mnt --net=/host/proc/1/ns/net --uts=/host/proc/1/ns/uts -- <command>`. Use `docker exec -i` when streaming scripts. Use Nexus's existing iragonforce SSH settings and tailnet Hostname override rather than copying its private keys. This is powerful host access; scope commands narrowly.
- Qubit's maintained client routing is ~/.ssh/homelab-routing.conf, included first by ~/.ssh/config, using ~/.local/bin/homelab-ssh-connect. Inspect current files before edits. Helper selects a connected TCP socket with bounded LAN-first/tailnet-second attempts; OpenSSH retains authentication and host-key verification. Never rerun a failed remote command or fall back after a host-key/authentication failure. TCP-only fallback does not cover successful-connect/banner stalls; document that limit.
- Exercise ordinary ssh alias, explicit LAN/tailnet aliases and SFTP. When Wi-Fi source is blocked but Ethernet works, the helper's --lan-source diagnostic option can exercise genuine fallback without network changes; tailnet attempts must not inherit that LAN source bind. If a target is offline during deployment, mark its authentication tests pending and retry ordinary and explicit-path aliases with fresh connections once it returns; a timeout on an offline host validates neither auth nor the helper. Keep actual off-site validation explicitly pending until exercised.
- For key-agent migration, inventory only public key filenames/fingerprints, live agent public identities and effective `ssh -G` identity/agent settings; never read or transmit private key material. Compare key type + public blob locally to establish whether vault identities match the host's configured keys. A responsive agent or successful ordinary SSH does not prove the agent signed: ordinary SSH may silently use a local private file.
- Test one target at a time with the chosen agent socket and a public-key-only `IdentityFile`, strict trusted host key, explicit `IdentitiesOnly yes`, and debug lines identifying an `explicit agent` offer, server acceptance and successful authentication. Isolate the test from the normal config with `-F /dev/null` when needed, explicitly carrying over the route ProxyCommand, host-key alias and known_hosts path. Bound the attempt; if the agent may be waiting for GUI approval, distinguish a timeout from an authentication rejection and coordinate with the user before retrying. Only after each forced-agent path succeeds should you switch normal aliases; preserve old local-key login until readback and fresh sessions prove rollback works.
- For Bitwarden on macOS, follow `references/bitwarden-ssh-agent.md` for import/generation, socket placement, authorization modes and proof-of-agent recipe. User handles vault unlock and private-key import locally; no private material through Hermes. Never disable working key or host access merely to prove the agent.
- Back up SSH config privately before edits, validate candidate with ssh -G before installing, then read back deployed files and perform fresh connections. Rollback must not delete unrelated known_hosts, identities or agent settings.
- Append change/rollback/evidence to canonical Qubit kit CHANGELOG.md and access context. Do not run full sync blindly while a host is offline; it can touch tmux state. Record deferred mirrors.
