# Homelab host operations

## When to Use

Use for host-specific software troubleshooting, SSH-agent integration, and cross-host operations involving Nexus, Qubit, or Tensor.

## Procedure

1. Identify both the displayed client and the tool execution environment before running commands. Run Nexus-container inspections directly with the terminal: Hermes tools execute in Docker on Nexus. Do not SSH to Nexus merely to inspect the current container; an SSH timeout to a host address says nothing about local container access. If host-OS access is needed, distinguish that explicitly and select a host-access path.
2. For Qubit and Tensor, use their current SSH connection to inspect target software. Noninteractive SSH shells may omit package-manager paths; check known absolute binary paths or login-shell configuration before concluding a program is missing.
3. Reproduce the exact user-visible symptom, inspect the relevant config and upstream command output, and change only the failing component. For container-to-container integration failures, start with the failing run's bounded log and its endpoint, then probe DNS/TCP/HTTP from the caller container and correlate with the receiver's logs at the same time; a socket close alone does not establish which component failed. Read only named configuration fields and metadata needed for the probe. Never dump a container's full environment or private config: these routinely contain live authentication and signing secrets, and tool output can expose them in the conversation. Filter locally to variable names or redacted values, and avoid searching broad private trees when an exact run-log path is known. For gateway failures, separate transport (`/health` from the caller), authenticated route validation, run acceptance, and execution/event delivery. When runs must not be started, POST intentionally invalid `{}` to `/v1/runs` with the caller's configured credential: an expected authenticated validation error (such as `Missing 'input' field`) exercises the relay and route without admitting work; verify in the handler that validation precedes run creation and confirm no new run appeared. A successful probe with Hermes's own key does not prove the encrypted Paperclip credential matches it; use the actual caller credential where possible, without displaying it. A healthy endpoint or a GET returning 405 proves neither authenticated request acceptance nor execution. Record each probe's result once, then move to the next untested boundary instead of repeating identical environment dumps or endpoint checks. If an iteration or time budget is approaching, stop probing and report the strongest supported conclusion, what remains uncertain, and the next discriminating check; never end with an empty summary. If a custom CLI module fails because its data source is unavailable, compare the CLI's native module before inventing another parser. For Paperclip agent incidents or autonomy audits, inventory agents, issues, tool connections, and runtime health through authenticated API calls before changing status or restarting a task. If the user requests updates through an existing outbound-only message connection, reuse that route rather than provisioning a competing receiver; verify publication by reading back its status, distinguish provider acceptance from human receipt, and mirror questions requiring replies in a channel the user can answer. Do not make bidirectional messaging a prerequisite for unrelated authorized audit or implementation work. Inspect each GET handler before classifying it as read-only: quota-status projections may invoke provider CLIs, while recovery projections may revalidate and resolve persisted actions. Prefer direct source-contract inspection and truly passive collection endpoints when execution or writes are disallowed; see `references/paperclip-agent-runtime.md` for audit and recovery interpretation. When the user wants unattended operation, identify the exact approval boundary (adapter CLI, sandbox, board policy, or tool scope) and remove only the intended prompt after explicit authorization; do not translate frustration with approvals into unrestricted company-tool grants. Read back the saved settings and evaluate the exact tool request through the board's policy-test endpoint without consuming rate limits or writing audit events; separately verify connection health and an actual run only when execution is authorized. When the failure is a model credential or adapter error, inspect the agent's actual adapter type/config and the provider's authentication mechanism before changing it: an API-key adapter will not use an OAuth login held by another application. Check the Paperclip runtime user's home, installed adapter metadata and CLI availability; provision only the required credential into Paperclip's private persistent store with restrictive permissions, then run a bounded non-destructive authentication probe as that user without displaying tokens or account details. Installing an adapter and proving CLI authentication do not switch the agent or prove an agent run: update the agent via its supported interface, read back the exact adapter config, and verify a real run only when the user authorized execution. Do not report the agent repaired while it still points at the old adapter. The connections collection is an object with a `connections` array; do not treat it as a top-level array. Correlate a failing MCP connection's configured endpoint with the caller and target containers' live network attachments, listening ports, and service logs; a container IP can resolve while the requested port refuses because it belongs to a different service. Distinguish agent error/paused state, issue workflow status, and an active execution run; never infer that an issue marked in progress is currently running. If asked not to restart tasks, avoid wakeup, resume, run, or retry endpoints. Before clearing a persisted agent error, confirm the error is stale and there are zero live runs, then use the supported clear-error action and read back the agent status, issue status, and live runs. Leave queued recovery actions, issue comments, and blocked issues untouched unless explicitly requested; clearing a persisted agent error does not clear historical failed runs or prove a repair. If the user still sees the exact error, inspect its timestamp and source (current agent state, failed run history, or queued recovery) before calling it fixed. If a Paperclip prompt shows a completed duration but no transcript, inspect the exact run's status, result response, presentation resolution, denied actions, and issue comments before treating a successful exit as a delivered answer. Compare the saved agent permission settings with the adapter's actual CLI flags: a test harness may force auto-approval even when production does not, so its passing probe can miss a headless approval denial. With authorization, change only the approval setting and retain the existing sandbox; read back the config and run a bounded tool-using probe as the runtime user. Treat that probe as CLI validation, not proof of Paperclip's heartbeat/comment pipeline; verify a fresh Paperclip prompt separately when authorized, without retrying unrelated completed issues. See `references/paperclip-agent-runtime.md` for the diagnostic decision path, workspace-validation recovery, and safety boundaries. When tasks must not be started, use the non-admitting authenticated validation probe above, then report valid-run acceptance and execution as unverified rather than retrying work.
4. Respect the requested write scope, including an explicit no-backup constraint. Verify by rerunning the original command on the target host, not by checking only syntax or a nearby probe. State what changed and any unverified boundaries.
   - For a new Nexus Docker service, inspect the live Docker networks, occupied addresses, neighboring maintained Compose files, source bind paths, and upstream deployment requirements before allocating an address. If SSH to Nexus from Hermes's container times out, use the already-mounted Docker socket with a disposable container binding only the necessary host directories; use `--network host` for host-side macvlan reachability checks. Do not mistake container-network SSH failure for host unavailability. Keep Compose and generated secrets on host paths with restrictive permissions, pin the image digest, and preserve existing services. If the local Docker client lacks Compose, a disposable Docker CLI image with the socket and Compose directory mounted can run `docker compose -f /stack/compose.yaml --project-directory /stack up -d`; use the same project identity for subsequent changes and rollback. After startup, allow first-run migrations, then verify container state/restarts, network IP, HTTP UI and health from the host network; a successful create or an early connection refusal is not a readiness verdict. Report bootstrap, HTTPS requirements, backups and client-side reachability as separate unverified boundaries. When the user asks for installation first, return the verified URL before attempting optional integrations.
   - For internal CA and HTTPS deployments, first discover whether a CA already exists and preserve its root identity; check its durable state, separately protected root key, recovery archive, DNS records, proxy routes, ACME client support, and application trust before changing any component. Follow `references/internal-ca-and-tls.md` for issuance, DNS, proxy, and client-trust verification.
   - If Hermes's VLAN 5 container cannot route to a client, check connectivity from a disposable `docker run --rm --network host` container using an already-local image. Mount only the existing Nexus SSH directory read-only, retain strict host-key verification with the known host-key alias, and use the Nexus host identity when the dedicated Hermes key is source-restricted to LAN. Never copy or display private keys or bypass host-key checking.
   - For Syncthing GUI resets, the on-disk GUI password is a bcrypt hash, not recoverable plaintext. Back up the previous hash privately, deliver a generated new password to the requested client via SSH stdin into a mode-0600 file, then PUT only the GUI configuration using its API key. A successful PUT can return an empty body and trigger a brief GUI restart: do not parse the PUT response as JSON; retry subsequent GETs during restart. Verify the active bcrypt hash matches the new credential and verify the remote file without printing either secret. If a post-write check fails, restore the old hash and confirm rollback before removing the new credential file.
5. For a tailnet-only web UI, inspect the existing Tailscale Serve handlers and GUI authentication before exposing anything. Save the existing Serve JSON privately, add only a free HTTPS port with `tailscale serve --bg --https=PORT http://BACKEND`, and never run a global Serve reset. Check from another tailnet node with valid TLS, an HTTP 200 app page and rejection of unauthenticated private API calls; compare prior Serve handlers to readback. Report browser-login, tailnet ACL and reboot-persistence limits separately.
6. For SSH-agent migration, separate the terminal emulator, client, vault agent, remote host, and container. Inventory installed desktop agent/socket and `ssh -G` identity policy on each client before installing or changing keys. Preserve existing working keys, source restrictions, launcher dependencies, and recovery access while adding new public keys; never expose private key material or vault contents. Keep forwarding opt-in per trusted connection because a remote process can request signatures while the socket is forwarded, and it cannot replace unattended host-local authentication. Follow `references/ssh-agent-migration.md` for Bitwarden-specific decisions and verification.
7. For Nexus NPM failures affecting public domains, trace Cloudflare → cloudflared → NPM → upstream, test Nginx's running listener separately from `nginx -t`, and follow `references/npm-proxy-recovery.md` before editing stored or generated configuration. For local UniFi DNS and Nexus NPM/step-ca integration, first inspect the existing DNS policies and NPM proxy hosts: many `homelab.lan` A records point directly to fixed Docker IPs, and a wildcard DNS/certificate alone cannot route web UIs on different ports. The official local UniFi API uses the already-private Nexus user key reference under `~/.secrets/udr7-api-key.json` (do not print or copy values) and `/proxy/network/integration/v1/sites/{siteId}/dns/policies`; list all pages, read before PUT, send all intended fields explicitly, and GET the exact policy afterward. The UDR7 management TLS leaf is self-signed with CA:FALSE: pin its observed DER fingerprint before presenting the API key and compare the peer certificate on each connection rather than silently disabling verification. NPM's running master is UID 568, so cert directories and private keys must be readable by that owner; `nginx -t` as root can pass while an `nginx -s reload` silently fails with `cannot load certificate` in `/data/logs/fallback_error.log`. Confirm the live HTTPS response after reload. For local-only hosts deny untrusted sources at the Nginx server and test the cloudflared namespace is rejected. Step-ca ACME HTTP-01 can use NPM's existing `/data/letsencrypt-acme-challenge` webroot. Treat short-lived leaf expiry as an operational gate: inspect every served leaf's `notAfter`, recent timer results and the next scheduled trigger, and verify actual rotation before relying on unattended renewal. If a leaf is already expired, back up the active key/cert set privately and follow the reissuance path in `references/internal-ca-and-tls.md`; merely fixing DNS and rerunning `step ca renew` does not recover an expired leaf. Avoid moving direct service DNS names without an explicit legacy alias and a verified proxy path.
8. For cross-host Syncthing reconciliation, compare folder IDs, labels, actual paths, peer lists and REST `/rest/db/status` on every host; equal labels can hide distinct datasets. Back up private configs and affected data before reassigning IDs or changing authority; removal of a folder entry leaves data but may remove its `.stfolder` marker, so restore the marker before scanning a replacement mapping. Disable peer `autoAcceptFolders` if duplicate offers are being recreated. `/rest/config` PUT may return an empty body, so check status and then GET for verification rather than JSON-decoding the write. When one node is authoritative, pause the folder across hosts, back up each dataset, set the source send-only and recipients receive-only, then run source `/rest/db/override?folder=ID` before resuming recipients. A receive-only recipient can delete its extra live files to follow the source: keep its full pre-change archive until content has been reviewed, not merely until the GUI reports idle. Verify exact folder IDs, all expected device memberships, paths, errors, and eventual local/global convergence on every host; a configured share is not completed data transfer.
