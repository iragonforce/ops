# Internal CA and service TLS

1. Inspect live Compose labels, mounts, networks, listeners and proxy-generated configuration before planning a CA. If a CA already exists, record the root fingerprint and its backup locations; never rerun CA initialization to fill in a missing integration. List secret filenames and permissions, not their contents or encrypted provisioner blobs. Check that a recoverable archive includes configuration, intermediate key, provisioner credentials and database, and that the separately stored root key is recoverable without placing it in Git.
2. Query the authoritative local DNS server from a host-network namespace as well as testing client resolution. Compare existing records with live service addresses and route consumers before changing an address; a name pointing directly to a container may be intentional. If the user points to an existing router API key, inspect the private file's shape without printing its value, then authenticate from an isolated host-network process that mounts only that secret read-only. For UniFi Network, list site IDs via `/proxy/network/integration/v1/sites`, then page through `/proxy/network/integration/v1/sites/{siteId}/dns/policies`; create with POST and update existing policies with PUT only after saving their exact prior fields. Send `X-API-Key` in a request header, never in command-line arguments or logs. A UniFi self-signed management leaf may lack CA capability: pin and check its exact DER certificate fingerprint immediately after the TLS handshake and before transmitting the key instead of treating unverified TLS as a durable shortcut. Read back each changed policy by ID and query the authoritative resolver from Nexus and another LAN client. Preserve a direct-service DNS name with a new alias before migrating its old hostname to the proxy, then check clients that used the old hostname with a nonstandard port. When DNS write access is unavailable, leave the record untouched and label dependent HTTPS checks blocked rather than substituting a hosts-file override as proof of normal resolution.
3. Distinguish CA health, ACME directory discovery, JWK issuance, ACME issuance, proxy TLS, and runtime trust as separate gates. `step ca health --ca-url URL --root ROOT` and `step certificate fingerprint ROOT` check the CA; `step ca certificate NAME CRT KEY --provisioner ADMIN --provisioner-password-file FILE --ca-url URL --root ROOT` checks JWK issuance only. Verify SAN and issuer, then `step certificate verify CRT --host NAME --roots ROOT --issuing-ca INTERMEDIATE`; remove temporary private keys. A directory GET does not prove ACME challenge or automatic renewal.
4. Inspect the actual proxy certificate mechanism before selecting automation. If its built-in client cannot use a custom ACME directory, use a separate step ACME client against the internal directory and a durable renewal path; do not equate an issued one-day certificate with completed automation. In Nginx Proxy Manager, the existing `/data/letsencrypt-acme-challenge` webroot and `conf.d/include/letsencrypt-acme-challenge.conf` may serve HTTP-01 without replacing NPM. From the CA container itself, resolve each challenge hostname and fetch a temporary token over HTTP before issuance: Docker DNS can forward private names to a public resolver even when LAN clients resolve them correctly. If the CA cannot resolve or reach the public-facing hostname, add narrowly scoped container host mappings to NPM's verified stable backend IP, then recreate only the CA container and confirm its root fingerprint and health. Do not change LAN DNS or proxy ACLs merely to make the challenge work. `step ca certificate NAME CRT KEY --acme URL --webroot WEBROOT --root ROOT` exercises ACME; verify the resulting chain. Construct the fullchain from leaf plus intermediate, protect its key, and ensure the Nginx master UID can traverse certificate directories and read both files before reload. `nginx -t` run as root can pass even when an unprivileged master logs a certificate permission error and keeps serving its old configuration; inspect the error log and test the live SNI endpoint after `nginx -s reload`. Back up proxy configuration; never replace unrelated working routes. Schedule renewal only when requested. For each served leaf, inspect `openssl x509 -in LEAF -noout -dates` together with the timer's last trigger and recent service journal; exercise the service, then verify an actual rotation and Nginx reload rather than assuming an enabled timer proves rotation. Keep the CA hostname resolvable in the renewal process's own network namespace: a correct LAN DNS policy does not guarantee a host-network container using public DNS can resolve the private name. If a certificate is already expired and `step ca renew` rejects it, stop retrying renewal. Back up the exact active certificate/key set with restricted permissions, issue a replacement using the previously validated ACME HTTP-01 webroot or authorized JWK provisioner as appropriate to that host, verify its SAN and chain, and only then atomically install it with the Nginx master's required ownership, validate configuration, reload, and check live SNI/expiry. Do not call that recovery complete until the HTTPS client succeeds with normal trust and the next unattended renewal path has been exercised; if reissuance has not been performed, report it as pending rather than presenting these steps as a tested fix. Test TLS with `curl --cacert ROOT https://NAME/`, not `-k`; an HTTP 403 after valid TLS may come from the upstream application's host allowlist, so check proxy access/error logs and upstream headers before changing network ACLs.
5. Install the public root in each requested host's native trust store and verify a normal TLS request on that host: Debian uses `/usr/local/share/ca-certificates/` plus `update-ca-certificates`, while Arch uses `/etc/ca-certificates/trust-source/anchors/` plus `update-ca-trust extract`. A host trust update does not change an already-running container's trust. For container clients, inspect both application and CLI trust: Node's `NODE_EXTRA_CA_CERTS` can point to a PEM bundle, but curl/OpenSSL may need the system store or `SSL_CERT_FILE`. Append the new root to any existing extra CA bundle rather than replacing other trusted roots, persist the configuration across recreation, and verify from inside the actual application container with its normal trust store and no TLS bypass. If an HTTPS request verifies yet the upstream returns 403, check its allowed-hostname setting before blaming the CA. Distinguish HTTPS transport from upstream API-key authentication.
6. Restart only the CA container if persistence validation is requested; compare the root fingerprint before and after, wait for healthy, and leave host reboot untested unless explicitly needed. Verify DNS from another LAN client and end-to-end application calls separately before reporting completion. Record exactly which gates remain blocked and what access or decision unblocks them.
