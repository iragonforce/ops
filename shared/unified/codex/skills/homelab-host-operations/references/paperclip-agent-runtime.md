# Paperclip agent runtime and task recovery

Use this when an agent run has no usable transcript or issue reply, or a task fails workspace validation. Keep diagnostics bounded and avoid dumping raw private configuration or response bodies.

1. Locate the exact run behind the UI event. Read run status, exit code, `resultJson.response`, presentation resolution, `denied_actions`, retry history, and associated issue comments. A successful process exit with `no_user_facing_response` and no comment is an empty delivery, not a resolved prompt. Confirm whether the issue itself is done or active before considering any retry.
2. Read the agent's saved adapter type, model, CLI path, sandbox and approval settings, plus the adapter's actual invocation flags. Distinguish model/auth failure from command approval denial. A standalone adapter environment probe may silently pass `--dangerously-skip-permissions`; compare its flags with the saved production configuration before trusting it as an end-to-end check.
3. If the run denied a command and production CLI approval is off, obtain the user's authorization for unattended tool approval. Change only that setting through the supported agent API, preserve sandbox mode, and read back the exact agent config. Explain that sandboxing limits execution scope but auto-approval removes interactive tool confirmation. Roll back this setting independently by restoring its prior boolean; do not restore an older whole-agent snapshot unless the full adapter migration is being undone.
4. Run a short, non-destructive tool-using CLI probe as Paperclip's runtime user in its actual workspace, with the same approval and sandbox flags. Parse structured output for the tool step's completion, result status, denial count, and expected reply marker; do not infer success from exit code alone. Do not expose tokens or account details in diagnostic output.
5. A CLI probe validates only the CLI boundary. When task execution is authorized, send a fresh bounded Paperclip prompt and inspect its run result, presentation and delivered comment/transcript. Do not wake or retry a completed issue simply to prove the adapter works. If a fresh prompt was not run, report the Paperclip delivery path as unverified rather than repaired.

## Read-only autonomy and recovery audit

1. Inventory the current agent, project, issue, run, connection, tool-profile, approval, and scheduler state through authenticated APIs, recording the endpoint contract and whether the response is a current projection or historical record. Use actual runtime configuration and run history to distinguish configured capacity from exercised capacity; a queued issue or an `in_progress` issue is not a live run.
2. Before issuing an unfamiliar GET during a strict no-execution/no-write audit, inspect its handler and callees for subprocess launches, revalidation, logging, or writes. A quota projection may invoke provider usage CLIs; an issue recovery projection may resolve an obsolete action and log activity. Avoid those endpoints when their side effects conflict with the audit boundary. If one was already called, inspect bounded activity for effects and state the evidence limit rather than assuming a GET was passive.
3. Reconcile counts by comparing API semantics before treating them as inconsistent. An active-only issue recovery response can be empty while company observability retains historical recovery actions. Record the denominator, time window, and pagination for each count; never interpret empty current projection as missing history.
4. Pin source provenance against the deployed revision using the upstream commit API, then hash-compare selected deployed source and manifest/lock files with the public commit. Report a lockfile delta separately even if the runtime code matches; matching a few source files does not prove full image parity, and an upstream lockfile may omit dependencies present in the running build.
5. Preserve a sanitized evidence index and rollback/access-dependency note. Do not promote an existing backup inventory to a recoverability claim without an isolated restore. Keep production implementation gated when maintained deployment inputs, exact source provenance, or effective instruction/tool-policy precedence cannot be verified. If host access is needed, request a narrow read-only mount of named configuration directories rather than broad host-root access, and read named nonsecret fields only. For Compose inspection, use an already-local disposable image with `--network none --read-only --cap-drop ALL --security-opt no-new-privileges` and `--mount type=bind,src=<existing-named-dir>,dst=<inspection-dir>,readonly`; omit the Docker socket and parse YAML structurally before counting services. A regex over YAML can mistake nested properties for service names. Reduce output to selected nonsecret keys (environment variable names, not values) and source hashes, and keep raw Compose text out of shared evidence.

## Photon replies saved but no answer

1. Trace the existing authenticated endpoint through conversations, inbound delivery, linked issue comment, inbound-wakeup action, wakeup receipt, run, and outbound publication. Read bounded records; preserve private message bodies outside shared evidence. A processed delivery can still have a skipped wakeup. Check the actual wakeup reason before blaming provider intake or live-session binding.
2. If the chat is bound to a dependency-blocked issue, keep those task dependencies intact. When Coordinator execution is authorized, verify the deployed linear chat controls; supported standalone `/status` answers without inference, and `/new` releases only the conversation generation after its control reply is delivered. Ask the owner to send `/new`, wait for its acknowledgement, then send a fresh harmless request. During an owner stop/configuration hold, suspend `/new` and autonomous reply tests and use explicitly manual Board publications for updates instead. Do not forge an inbound owner command, replay old skipped wakes, or mark unrelated blockers complete to repair communication.
3. Verify a real linked-owner inbound message, the new conversation/issue without the old dependency, the Coordinator run result, and the exact outbound answer. Claim autonomous conversation only after that chain succeeds; outbound provider acceptance alone is insufficient. A CLI agent manually reading Board comments and publishing a reply is an explicit manual relay, not a persistent live-session binding.
4. Keep the existing single receiver and identity. Distinguish a phone-to-Paperclip conversation from the classic CLI: without a supported in-process input/attach endpoint, Paperclip wakeups cannot inject a new turn into that running CLI. Use the existing Paperclip-managed Coordinator as the supported phone surface and report model/quota or runtime blockers separately.
5. Reconcile an outbound POST timeout before sending again. Derive the exact stored key from the inspected handler: explicit Board publications currently namespace the client key as explicit-board:<endpointId>:<conversationId>:<clientKey>. A query for only the bare client key can falsely report absence. Read that scoped native record, recover its publication ID, and GET its exact batch status; a published receipt can exist even when the original caller never received an acknowledgement. Keep provider publication separate from owner-read or autonomous-conversation evidence.

## Full Paperclip stop and durable owner holds

1. Save a private minimal before-state, then pause every nonterminated agent through the supported Board pause route; include the Coordinator and any agent named Hermes. This does not stop a standalone Hermes CLI or its isolated fixtures. Inspect the list contract before counting: the current company agent list excludes terminated rows and exposes no include-terminated query. Read retained terminated agents by their exact known IDs and reconcile the combined roster against authoritative passive counts; do not infer disappearance or pass invented pagination/query options. Read back each changed exact target.
2. Verify running, queued and scheduled-retry runs plus queued/claimed wakeups separately. A paused roster can coexist with a scheduled quota monitor. When the owner ordered all work stopped, cancel remaining runs through the supported Board operator-cancellation route, save their lineage privately and read back cancelled; the operator stamp lets native recovery stand down. Recheck the aggregate after subsequent work rather than inferring zero work from idle/error task cards.
3. Preserve owner holds through recovery, health/reset arrival and service startup. Inspect late agent-status writers for a guarded SQL UPDATE: an earlier read that saw idle does not prevent a concurrent pause being overwritten. Protect paused, terminated and pending-approval states in the write itself; prove the race in isolation before deployment. A source repair is not a production repair.
4. Reactivate only after the owner's configuration/acceptance gate permits, then selectively admit eligible work. A saved pre-hold roster is rollback evidence, not a bulk-resume or cancelled-retry replay queue. Keep Photon reply tests suspended while inference is stopped.
5. Check deferred-recovery loops before their first write, not only before provider dispatch. A held agent's interrupted or stranded wake can have its timestamp, receipt or saved input mutated without starting a run. Exercise both loops with real PostgreSQL and compare complete wake/agent/run records across repeated sweeps; retain paused, terminated and pending-approval records unchanged. A fresh pre-loop status check is preservation, not a substitute for committed final admission.

## Native quota continuation implementation checks

1. Serialize immediate and fallback retry creation on the same company-scoped issue → failed-predecessor locks, then inspect all successor states before creating another. Commit the successor, existing wake linkage, required lifecycle receipt and recovery-action linkage together. Repair the action link when reusing a successor; a completed/cancelled successor is not permission to resurrect the predecessor. Preserve recorded session/checkpoint metadata and issue workflow disposition independently.
2. Use the current agent row from the same company/org snapshot when evaluating database-backed invokability. Treat a caller-supplied row as an identity hint, not fresh status or reporting authority. Exercise committed pause/termination/pending-approval, changed parent, deletion and wrong-company cases; a fresh ancestor list does not repair a stale direct agent object.
3. Model temporary eligibility waits separately from terminal suppression. Keep pending questions/approvals and manual agent/company holds parked in the native scheduler without consuming probe/retry attempts, resolving human input or clearing the hold. Let terminal task cancellation/completion win over a simultaneous temporary pause. Check both read-only eligibility and state-changing promotion; retry-now must report the persisted held row rather than falsely claiming promotion.
4. Classify quota successors from their company-scoped durable predecessor as well as explicit retry/wake metadata. Classification only tightens guards; it does not verify account/model identity or authorize provider work. A shared credential-store path with fallback/pooling is not a physical-account binding. Conservative namespace grouping requires explicit owner policy and must remain labeled as grouping, not account equality or model entitlement.
5. Distinguish promotion, synchronous adapter callback invocation, committed admission and actual provider send. Await fresh authorization at each controlled work-unit launch/turn boundary; a notification-only void callback is not a gate. Trace optional hooks through logging shims and every alternate executor: test the real outer adapter with harmless child effects, because forwarding to a direct CLI attempt does not cover ACP/native/warm-session bypasses. Define the real guarantee: governing changes serialized before final admission block new starts; later revocations require cancellation/reconciliation. A local database commit cannot prevent every later remote byte or gate all internal inference in an opaque executor. Never hold database transactions across provider I/O or treat an expired lease/dead owner as proof of absent effects. Verify the installed gateway's request-key lookup and replay-retention contract before retrying an uncertain request.
6. When a fully mocked adapter suite fails before dispatch, inspect credential preflight and compare the exact failures against the prior source checkpoint in a networkless fixture. Use an explicitly inert test-only value in that fixture when readiness is merely setup for the mock; preserve the production credential gate and never import real credentials. This tests scheduler wiring, not provider authentication or model availability. Run embedded PostgreSQL suites as the fixture's non-root runtime user, verify zero skips, and resolve package-local tool entrypoints before installing anything.
7. Enter company admission serialization at the outer transaction boundary before issue/wake/run/quota locks. Reuse the exact guarded transaction for same-company service composition; audit raw outer callers before wrapping lower layers. Lifecycle callbacks that require a committed change must run after the root transaction, not after a savepoint. Audit adapter metadata/schema/secret preparation too: a configuration callback can perform external I/O even when it is not a provider execution. A tested writer subset is not a universal fence, and failing formerly supported nested/hire paths closed is a release compatibility blocker until repaired.

## Effective reporting instructions

1. Trace the deployed adapter's actual instruction precedence before editing files. Hermes gateway execution uses adapterConfig.instructions before payloadTemplate.instructions and does not read the configured managed AGENTS.md; edit the inline string with an explicit shallow-merge PATCH. Managed Codex/Antigravity entry files use the instruction-bundle file API with a freshly read baseRevisionId. Preserve unrelated configuration and existing role/safety/learning text.
2. Capture exact prior parents and effective instruction bytes privately before routing changes. Validate unique same-company IDs, every ancestry chain and each serial forward/rollback intermediate for cycles and missing parents. Change only necessary reportsTo edges, preserve terminated rows/status holds, and read each exact target back.
3. Treat single-spokesperson instructions as behavioral routing, not a universal outbound security ACL. Verify native endpoint assignment separately. Use compact specialist handoffs with outcome, evidence, uncertainty, next decision and rollback; keep the Coordinator's human summary distinct from internal technical records. Configuration readback does not prove future compliance or a measured style improvement.
4. Keep a per-write intent/readback journal and stop on drift or conflicts. A failed acknowledgement can follow an applied write; inspect its exact target before retrying. Retain deferred wakeups as historical/current scheduling evidence, not permission to replay them.

## Pinned offline repair artifacts

On resuming an undeployed branch, inspect the current production image ID and compare the selected compiled runtime files against the preserved baseline before building. Independently deployed hotfixes may exist only in compiled output; a source-only Git comparison can miss them. Capture private provenance/diffs, preserve working fixes in the candidate with regressions, and refresh the release/rollback baseline. A selected-file match is not whole-image equivalence; never overwrite newer production merely to restore an older checkpoint.

Use an immutable original image plus allowlisted committed source overlays when its build refreshed the public lockfile: preserve its installed dependency tree rather than resolving today's dependencies. Confirm source exports versus compiled runtime paths independently. A server source overlay must include compiled output and matching source/declaration maps; direct installed compiler entrypoints avoid Corepack downloads and unwanted native-runner rebuilds. Build networkless without production data/credentials, then verify payload/lock hashes and actual module imports under the intended UID. Give a read-only smoke probe an explicit writable scratch/TMPDIR, and distinguish module import from application boot and agent execution. If a resumed executor is root, retain repository ownership for Git writes and restore only task-edited files whose atomic edit changed ownership; never recursively chown the tree or add global safe.directory trust.

## Board access for an existing coordinator

1. Inspect the coordinator's current agent permissions, assigned/desired skills, skill configuration state, and live runs through authenticated read-only Paperclip APIs. Treat the board skill and board write permissions as separate gates: a configured skill does not grant `canAssignTasks`.
2. Discover the supported agent-permissions write route and payload from the running API contract. Save a private rollback record of the exact prior permission object, then set only the missing capability, preserving existing flags explicitly. Do not add a connection, credential, skill, or agent when the built-in board skill is already assigned.
3. Read back the exact agent's permissions and skill state and confirm live-run count. A desired/configured skill may only enter the effective runtime on the next run; do not claim it has been exercised until a permitted run proves it. Do not wake a waiting issue merely to validate a permission grant; report execution as unverified if no run was authorized.

## Board-managed tool approvals and scope

1. Inspect the coordinator's adapter approval/sandbox setting, agent permission object, assigned tool profile, applicable company policies, connection health, and live runs independently. A CLI auto-approval flag does not override board-managed tool policy; an allowed policy does not repair a refused MCP connection. Preserve default-deny and narrow tool grants unless broader access was explicitly authorized.
2. Discover the running board API's policy/profile routes and schemas from its OpenAPI document. Save a private rollback snapshot of the exact policy or profile before writing; change the narrow rule causing the prompt rather than creating an unrestricted profile. Keep other agents' policies and all unrelated capabilities unchanged. Do not print bearer credentials or private connector configuration.
3. Read back the exact policy/profile and test the intended actor, connection, catalog entry, tool name and side-effect classification using the supported policy-test endpoint with rate-limit consumption and audit writing disabled. Check its decision and reason code, not just HTTP success; confirm neighboring agents' rules and the live-run count remain unchanged. Test connection health separately. An allow decision proves policy evaluation only, not connector reachability or successful execution.
4. Run a bounded real tool invocation only if the user authorized execution, then inspect its run and delivery. If the connector is unhealthy or no invocation was authorized, report those limits explicitly. Keep rollback steps with the private snapshot, and record the verified change in the canonical homelab journal.

## Workspace-validation failure and safe restart

1. Read the exact failed run's `errorCode` and detail, issue status, project primary workspace, issue execution workspace, agent adapter, recovery action, and live runs through authenticated read-only API calls. Distinguish an adapter launch failure from a Hermes service failure; issue status alone is not evidence of an executing process. Discover supported API shapes from the live OpenAPI document rather than guessing write endpoints.
2. Validate the configured cwd from the Paperclip runtime container, including `git rev-parse --show-toplevel`, permissions as its runtime user, and whether the workspace is a Git checkout. If the cwd is a migrated archive rather than a checkout, preserve it as a secondary read-only reference and prepare a separate task Git workspace; do not `git init` inside the source archive merely to satisfy validation. Record original workspace IDs, linkage, paths and a rollback procedure before edits.
3. Update only the primary project workspace and affected issue execution-workspace cwd to the verified checkout via supported APIs; read back both links and rerun the original workspace validation. Confirm zero live runs before clearing a stale agent error. Change blocked/recovery state and restart only with authorization. Recovery resolution can itself launch a run: read live runs and issue status immediately afterward before calling checkout/retry again. Treat a conflict from a later checkout as possible already-running work, not as grounds to launch a second run.
4. Check run history, live runs, agent status, issue execution phase and comments after restart. Paperclip may generate continuations after the initial successful run, so a successful run or `in_progress` issue is not a finished deliverable. If the final execution is `waiting_for_answer`, stop retries, quote the outstanding decision categories, and report explicitly what was and was not produced. Preserve a durable rollback note and note any unsynced canonical journal separately from the successful local repair.
