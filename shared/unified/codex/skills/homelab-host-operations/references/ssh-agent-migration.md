# Desktop vault SSH-agent migration

Use this recipe when introducing Bitwarden-managed SSH identities across desktop clients and a headless server. Check current vendor documentation before installation; client package paths and agent behavior can change.

1. **Inventory first.** Check desktop-app presence and agent socket on each workstation. Test a candidate socket with `SSH_AUTH_SOCK=/verified/socket ssh-add -l >/dev/null 2>&1` and record only exit status; `ssh-add -L` prints public identities and can still expose sensitive account metadata. `ssh -G <alias>` reveals `IdentityAgent`, `IdentityFile`, `IdentitiesOnly`, `ForwardAgent`, user and resolved host without opening a connection. Inspect client launchers and service accounts that currently depend on explicit keys. A noninteractive SSH shell may have no agent variable even when a GUI-session agent is working.
2. **Choose key ownership with the user.** Decide between importing approved existing OpenSSH/PKCS#8 private keys in the unlocked desktop app and generating distinct new Ed25519 keys in the vault. Do not copy keys into chat, shell command arguments, logs, shared config or temporary files. Installing the app is not vault enrollment; a user may need to unlock and approve agent signing. Do not reinstall an already working app.
3. **Set up client agents one workstation at a time.** Enable the SSH agent in the desktop app, select an authorization policy, and find its actual socket. Current Bitwarden examples: macOS DMG `~/.bitwarden-ssh-agent.sock`, macOS App Store `~/Library/Containers/com.bitwarden.desktop/Data/.bitwarden-ssh-agent.sock`, Linux native `~/.bitwarden-ssh-agent.sock`, Flatpak `~/.var/app/com.bitwarden.desktop/data/.bitwarden-ssh-agent.sock`, Snap `~/snap/bitwarden/current/.bitwarden-ssh-agent.sock`. Test from a fresh local terminal; configure `SSH_AUTH_SOCK` or a scoped `IdentityAgent`, but audit explicit `IdentityFile` and `IdentitiesOnly yes` first because they can constrain identity offers and defeat an assumed global agent switch. Bitwarden does not implement `ssh-add` key management or per-host selection of a vault key.
4. **Enroll public keys without lockout.** Add only approved public keys to destination `authorized_keys`, retaining existing entries, ownership/mode, source restrictions and verified host-key trust. Test each route using the intended agent before changing the next host. Keep original credentials for rollback until user-approved retirement. If several vault keys are offered, verify the server's `MaxAuthTries` behavior instead of weakening security globally.
5. **Treat headless access separately.** A desktop vault agent requires a running unlocked desktop session; a headless host or container does not gain an agent just by installing the Bitwarden CLI. For interactive nested SSH, offer one-off `ssh -A` only after the user accepts that a privileged remote process can ask the forwarded agent to sign for the duration of the connection. Confirm `ssh-add -l` status remotely without printing identities. Keep a separate local key for unattended SSH, launchers, scheduled tasks and disconnected sessions. Do not mount a workstation socket broadly into a persistent container or enable global `ForwardAgent`.
6. **Verify the whole chain and roll back narrowly.** From fresh workstation sessions, prove authentication to each intended host and Git endpoint, confirm server accepted fingerprint, test locked-vault and offline behavior, and exercise any SSH-dependent launcher and existing container-originated route. Record actual successes separately from planned tests. Roll back only new agent settings and public-key entries if needed; never remove known-working keys before replacement and recovery are demonstrated.

Official references: https://bitwarden.com/help/ssh-agent/ and https://bitwarden.com/help/about-ssh/.
