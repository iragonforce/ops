## Reboot validation

The first reboot exposed two startup defects: short-form OTBR bind entries were incompatible with Nexus's mount-checking stack launcher, and the bridge firewall generated invalid empty sets before all containers started. Bind entries now use structured sources with `create_host_path: false`; empty firewall sets omit the elements clause. All 50 containers recovered after these fixes.

The second reboot started all 50 containers with no failed systemd units. Checks passed for storage health, all VLAN gateways, DNS, service dependencies, traffic restrictions, Home Assistant integration states and the unchanged Thread dataset/OMR prefix. Qubit again passed both NFS read/write/rename/delete checks and all 27 HTTPS checks.

IPv6 host access needed explicit metric-10 routes through Nexus's macvlan shims because automatically received parent-interface routes selected the wrong local path. These routes are now persistent. IPv6 ICMP diagnostic policies now permit return traffic. Qubit successfully reached both `fd00:4::7` and the Thread OMR address `fd55:938c:141a:1:b5d:9043:9bac:b26` after those corrections.

The third reboot exposed a timing issue: explicit IPv6 source routes were added before duplicate-address detection completed, causing the VLAN unit to fail and dependent stacks to skip activation. The VLAN script now retries route installation for up to five seconds before requiring success. All stacks were explicitly recovered after that correction.

The fourth reboot passed VLAN initialization but exposed an intermittent `zfs mount -a` userspace abort in `fnvlist_lookup_string`. A subsequent mount attempt succeeded, but dependent stack startup jobs had already failed. Configured `/etc/systemd/system/zfs-mount.service.d/nexus-serial.conf` with `ZFS_SERIAL_MOUNT=1`, a supported [OpenZFS mount implementation setting](https://github.com/openzfs/zfs/blob/zfs-2.3.9/lib/libzfs/libzfs_mount.c), to avoid parallel mount execution. This is a mitigation for the observed abort; the precise upstream defect has not been established. Remove this drop-in and reload systemd to roll it back, after recording an alternative startup recovery method. Pool features, disk layout and data remain unchanged. A fifth reboot verifies this mitigation. Tensor's separate systemd/SSH blocker remains pending.
