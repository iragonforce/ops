# Three-host SSH over LAN and Tailscale — 2026-10-17

## Findings and changes

- Before changes, `ssh qubit`, `ssh tensor`, `ssh nexus` worked from Qubit. Tensor's `ssh qubit` failed because split DNS returned Qubit's stale Wi-Fi address 192.168.1.102; strict-key SSH to wired 192.168.1.4 worked. Nexus's `ssh nexus` failed host-key verification against its loopback-resolved name.
- Nexus had Tailscale SSH enabled (`RunSSH=true`). Tensor-to-Nexus SSH over its 100.x address stalled in Tailscale's browser check. Disabled only Tailscale SSH with `sudo -n tailscale set --ssh=false`; Tailscale networking remains enabled and Nexus's ordinary sshd listens on port 22. Qubit and Tensor then reached Nexus over 100.96.255.81 with existing OpenSSH keys.
- Set Tensor's `qubit` alias to 192.168.1.4 with strict checking. Explicit `qubit-ts`, `tensor-ts`, `nexus-ts` aliases on Tensor use their 100.x addresses and existing trusted host records. Tensor's `tensor` alias now explicitly uses its LAN address with strict checking.
- Added Nexus's `nexus`/`nexus-lan` and `nexus-ts` aliases, using its existing `qubit_ed25519` identity. Appended only that identity's public key to Nexus's own `authorized_keys` and added a local `nexus-self` known-host record. The local sshd public key matched scans of loopback and LAN. Added strict-key `qubit-ts` and `tensor-ts` aliases using Nexus's existing peer identities and trusted host records.
- Set Qubit's own `qubit` and `qubit-ts` aliases to its wired and Tailscale addresses with strict checking. Added a `qubit-self` known-host record from the local sshd public key after matching it to LAN and Tailscale scans. Qubit's existing key was already authorized locally. Qubit's existing LAN-first/Tailscale-fallback routing for Tensor and Nexus remains.
