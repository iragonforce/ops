# Hermes → Qdrant historical findings

Scope: default Hermes profile only. The main session database at container `/opt/data/state.db` (Nexus `/srv/containers/data/hermes/data/state.db`) is opened in SQLite read-only/query-only mode. The exporter `shared/scripts/hermes-compaction-export.py` selects parent sessions with `end_reason=compression` and summary-marked messages in their child sessions. Incomplete parent/child lineages are ignored until a later sync; a single read transaction gives the lineage query a consistent snapshot. Existing profiles' databases, `MEMORY.md`, `USER.md`, compression engine, and existing Qdrant origins are untouched.

`shared/scripts/qdrant-memory.py sync-hermes` uses the existing Qdrant collection and Tensor `qwen3-embedding:8b-fp16` model (4096 dimensions). It splits summary sections into individual Markdown list items, rejects oversized, multi-topic, sensitive, personal/financial and ambiguous items, and requires an exact public Git-tracked source path before indexing. Both existing credential expressions are applied. Rejected items are counted by reason but their text is never logged; they remain in the original protected session store only. This deliberately sacrifices recall rather than auto-publishing unreviewed private summary contents. A Git path is a traceability gate, **not proof that an agent assertion was true**. Automatically indexed points are tagged `agent_summary_historical_unverified`, `historical_only=true`, low confidence, original observation date and session/compaction/message IDs; the separately reviewed backfill has explicit review/verification labels. Before acting, consult current ops documentation and inspect live state. A path and a summary do not establish current configuration.

Each record uses a deterministic UUID based on the lineage and item ordinal, a SHA-256 hash of the screened text, and `origin=hermes_session`. The separate origin is filtered independently. Embedding batches are bounded to three; Qdrant upserts wait for acknowledgment and are read back before the per-compaction checkpoint advances. The checkpoint is an atomic, mode-0600 JSON file under the private Hermes container state path `/opt/data/state/qdrant-memory/hermes-compaction-checkpoint.json`; it contains IDs and an integrity digest, no transcript. A process lock in the same mode-0700 directory rejects concurrent runs. An interrupted temporary checkpoint file is safely replaced on the next locked run. Reconciliation compares IDs/hashes with Qdrant even after checkpoint completion, so interrupted upserts or missing points retry. No automatic pruning occurs. Qdrant or Ollama failure leaves the checkpoint at the last confirmed compaction; the next scheduled run retries. Do not expose private session data through the manual inbox or public Git.

The Nexus `qdrant-memory.timer` (15 minutes after previous inactivity, plus the existing path watcher at the last verified deployment) starts `qdrant-memory.service`. The existing inbox command still runs as `iragonforce`; an `ExecStartPost=+` command uses root only to enter the **existing** `hermes` container, executing the new sync as UID 10000, which owns the session database. The container uses `http://qdrant:6333`; the host inbox still uses its existing localhost endpoint. This is not a new scheduler or service. If the inbox command fails, systemd skips ExecStartPost and the next timer run must recover; monitor the unit result. The MCP source `shared/scripts/qdrant-memory-hermes-mcp.py` deploys to `/opt/data/mcp/qdrant-memory-hermes-mcp.py` in the container; it must admit `hermes_session` or the tool silently filters out those results. New TUI sessions discover the updated MCP schema; an existing session may need `/reload-mcp`.

Operator checks: `sync-hermes --dry-run` requires `QDRANT_MEMORY_INDEXERS`, `QDRANT_MEMORY_OPS`, and `QDRANT_MEMORY_QDRANT` set to the container paths/URL when run inside Hermes. Live automated runs use the unit's explicit environment. Review only protected staged findings, never whole summaries or transcripts in terminal logs. Qdrant `/points/count` with an origin filter and `/points` exact IDs verify write effects; `knowledge_search` with `origins=["hermes_session"]` and `knowledge_read` verify retrieval and provenance. A deliberately conservative selector may index **zero** findings from a compaction; that is safer than treating an unverified statement as an approved fact.

Backfill: the automatic selector quarantined unsupported items, while two distinct summary items were individually reviewed against public Git documentation, paraphrased as an incident and a decision, and added through the same bounded indexer. Their protected review manifests live under `/opt/data/state/qdrant-memory/review/` (mode 0600) and are **not** a watched inbox. The normal scheduler never prunes them. Do not interpret this one-time curated backfill as approval to index arbitrary older summaries automatically.

## Staged completed-chat selector (not yet deployed)

The task worktree adds `qdrant-memory.py sync-chat` alongside, not instead of, `sync-hermes`. The candidate scanner reads a query-only SQLite snapshot of the default profile's persisted TUI, CLI and Photon turns; it requires an assistant plain-text `finish_reason=stop`, an active user/answer pair, no subsequent failed-turn marker before the next user message, and a two-minute settlement delay. Cron, delegated and other-profile sessions are excluded. The installed `post_llm_call` hook lacks explicit completion/failure status fields, so the implementation uses settled persisted rows instead of adding a plugin. A protected forward-only `hermes-chat-checkpoint.json` must be explicitly bootstrapped to the current message ID before enabling the post-step; no historical chat is silently backfilled. The scheduled writer would use the **existing** hourly systemd timer/path unit and the existing Gemini provider (`gemini-3.8-flash-high`), Ollama embeddings, Qdrant collection and MCP bridge, with `hermes_chat` as a non-pruning origin. The existing read-only Gemini auditor is a separate job and cannot write or correct points; it must not be presented as ingestion.

Only bounded user/final-answer pairs passing two credential scanners, a personal-data gate and size limits would be sent to Gemini. Tool traces, intermediate thoughts, full sessions and rejected material are not sent or stored in Qdrant. Gemini returns at most two JSON findings; the writer validates text and topic again, embeds accepted findings locally, checks the exact Qdrant IDs/hashes, then advances the private cursor. It retries model/Qdrant failures without cursor advancement, deduplicates exact content hashes against the existing Hermes compaction origin, and never prunes. Points are tagged `historical_only=true`, `conversation_historical_unverified` and low confidence; model-selected claims still require authoritative source/live checks before operational changes. Privacy filters are conservative, not a guarantee against every unexpected personal string. A fresh MCP process is needed to load the new origin. The 34 affected unit/regression checks passed in the task worktree, and a direct authenticated synthetic model call returned two schema-valid facts. Live ingestion and end-to-end retrieval remain unverified pending deployment.

Any `hermes_session` removal requires explicit origin/ID verification, never collection-wide pruning.
