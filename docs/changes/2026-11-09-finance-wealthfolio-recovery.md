# Finance Wealthfolio recovery and second-host copies

Date: 2026-11-09. Objective: complete the owner-approved brief Wealthfolio stop, produce an encrypted app-consistent raw archive with its original master-key configuration, verify isolated restoration, and establish encrypted second-host recovery plus size-bounded private GitHub artifacts.

## Owner decisions and scope

The owner confirmed independent visibility of `FINANCE_BACKUP_GPG_PASSPHRASE_V1` in their own Bitwarden Secrets Manager infrastructure access without disclosing the value. The owner explicitly chose a **coordinated brief Wealthfolio stop** rather than the in-app export path behind Authentik/Cloudflare Access. This authorizes this manual capture/test only, not an unattended stop schedule. No financial import, reconciliation write, version upgrade, new persistent script, service or scheduler was performed.

## Wealthfolio capture and rollback

Preflight: `wealthfolio/wealthfolio:3.12.0` was healthy, used image ID `sha256:5790528fcd9795b571176cad78bcca09e3fa5875ec20968356586939e154c3cb`, and was the only running container mounting `wealthfolio-data`. The host `/opt/wealthfolio/.env` was mode 0600, contained the original `WF_SECRET_KEY`, and its parsed master-key value matched the running container in memory (neither value was printed). The matching Compose files and separate Authentik credentials file existed. There was ample capacity in the existing `/var/backups/homelab` destination.

The container was gracefully stopped with a 60-second allowance; its exited state was read back. The entire `/var/lib/docker/volumes/wealthfolio-data/_data` tree plus `/opt/wealthfolio/.env`, Compose files and Authentik credentials file were streamed directly through GnuPG AES256 symmetric encryption into `/var/backups/homelab/finance/wealthfolio-stopped-2026-11-09/wealthfolio-appdata-and-config.tar.gpg` (157,458,286 encrypted bytes). The passphrase was read from Bitwarden in memory and supplied via a pipe FD, never process arguments. No plaintext archive was written. The directory is 0700, files 0600; `manifest.json` holds source image, SHA-256, byte size and key reference, and a protected `verification.json` holds tests. A `finally` block restarted production even if archive creation failed. Readback confirmed the same image, Docker health and HTTP health; authenticated read-only MCP still returned four accounts with activity counts 5,035 / 3,209 / 426 / 0. Preserve the original running image, source data and config for targeted rollback; do **not** restore a snapshot over a live service.

## Isolated restore checks

The encrypted Wealthfolio archive hash matched its manifest. Its 20 validated members (15 regular files) were decrypted into a temporary mode-0700 scratch target and mounted into a temporary **network-none** Wealthfolio 3.12.0 container; all scratch and the container were removed afterward. The first diagnostic failed because Docker `--env-file` retained quotes around a value that Compose unquotes; the restored `.env` was parsed with its quoted values normalized in memory. The next attempt failed because OIDC issuer discovery cannot reach Authentik in a no-network namespace. The isolated clone therefore cleared the OIDC issuer/client settings **only in the test container**. A later health wait incorrectly expected Docker Healthcheck metadata provided by production Compose, not by the image; the actual HTTP health probe passed. A diagnostic MCP client initially pointed at the host's `:18088` port; correcting it to the clone's `:8088` made the final read succeed. These were isolated-test harness issues, not production changes or backup corruption.

The final isolated clone answered `/api/v1/healthz` and authenticated read-only MCP `get_accounts`/`search_activities`, returning exactly four accounts with counts 5,035 / 3,209 / 426 / 0. This proves the stopped-service encrypted archive, matching image, restored master key and account data work together. It does **not** test production Authentik/Cloudflare Access login, unrelated integrations, or every transaction/balance.

## Qubit and private GitHub copies

All six encrypted artifacts (the five from `docs/changes/2026-11-09-finance-backup-baseline.md` plus Wealthfolio) and four protected manifests/verification files were transferred via the existing strict-key SSH route to Qubit `~/.local/share/finance-infrastructure/backups/baseline-2026-11-09/{postgres-files,wealthfolio}`. Ten destinations totaling 814,488,136 bytes were individually read back by SHA-256 and size; files are mode 0600. Recursive directory creation left the intermediate `baseline-2026-11-09` directory at mode 0755 despite mode 0700 on its children; it was corrected and all relevant directory modes verified 0700. No raw statements or plaintext databases were sent. The encrypted Wealthfolio file was streamed back from Qubit, decrypted and fully parsed (20 members/15 regular files, original config and profile registry present), without extracting plaintext. The previously tested local file has the same SHA-256.

Private `iragonforce/finance-backups` received four **small encrypted** artifacts: Receipt Wrangler PG17 dump and files archive, finance analytics PG17 dump, n8n PG18 dump, plus a sanitized manifest and checksums. Each was read back byte-for-byte by authenticated GitHub API; private visibility was checked again. The Receipt Wrangler ciphertext was downloaded from GitHub, decrypted, restored into a disposable network-none PostgreSQL 17 container and returned one receipt/two items, then the container was removed. The GitHub README/recovery instructions were updated and read back. The 157 MB Wealthfolio and 656 MB n8n file archives are deliberately **not** regular Git objects; they remain encrypted on Nexus and Qubit. GitHub alone cannot recover the full stack.

## Remaining limits and recovery

This is a **manual baseline**, not a recurring backup system. No retention policy, scheduled job, persistent finance executable or application-level n8n/Receipt Wrangler login test was created. The n8n files tar came from a running app and was fully parsed but not restored as a functional app; cross-file consistency is unverified. Authentik/browser login for the isolated Wealthfolio clone was not attempted. Qubit is a separate encrypted copy but not an independent geographic/offline location. Financial-import completeness, balances and duplicate reconciliation remain unverified; imports still require a protected per-account dry-run and explicit owner approval.

For recovery, retrieve the exact artifact, compare its SHA-256 to the protected manifest, obtain the named Bitwarden key independently, decrypt into an owner-only target, and use the matching original image/config/DB version to verify isolated function before scheduling a production stop. The Wealthfolio raw archive includes its original server master-key configuration; it is **not** a portable `.wfbackup` export. The PostgreSQL archives are custom-format dumps. Never extract plaintext into Git or agent output and never overwrite live data during a test. Preserve both protected baselines and the Bitwarden key while these artifacts remain relevant. The enclosing ops commit is discoverable with `git log --follow -- docs/changes/2026-11-09-finance-wealthfolio-recovery.md`.
