# Tensor GPU ingress containment trial and rollback — 2026-11-26

**Objective/authorization:** The owner approved coordinated temporary interruption of direct Ollama (11434) and MinerU (7860) clients with rollback while moving these GPU paths behind admission. This was an ingress-containment trial, **not** a completed request-level GPU lease or permission to restart the failed llama service.

**Preflight:** Tensor `hermes-llama.service` remained failed/core-dumped; gateway, MinerU WebUI and wallpaper were active. Ollama's embedding model was resident at inspection; it was not stopped. `ss` showed no active connections to external 7860/8445. A persistent Tailscale-to-Ollama loopback connection was identified: Tailscale Serve HTTPS 8445 proxied to `127.0.0.1:11434`. Blocking only non-loopback port 11434 would not contain that path. Tensor's existing `tensor-control-guard.service` owns `inet tensor_control`; its `/etc/tensor-control/guard.nft` had no Git-owned source before this change. `hermes-llama.service` has a native-sleep drop-in that clears the base unit's broad `vram-purge --worker` prestart and substitutes a wallpaper stop, but still must not be restarted until a request gate and rollback are verified.

**Protected rollback material:** User-owned mode-0700 `~/.local/state/tensor-gpu-admission/serve-status-before.json` (mode 0600) records the original Tailscale routes. Root-owned mode-0700 `/var/lib/tensor-gpu-admission/` contains `guard-before.nft` and `nft-before.nft`. Original guard SHA-256 `275a91e93078f6073c4d9da807872c2e91c5e7e5cc7fac4ce3206da8209d27e1`. Do not print or publish these snapshots, and do not apply a whole nft ruleset over unrelated runtime changes.

**Changes made:** A temporary standalone nft input table first blocked non-loopback 11434/7860. `sudo tailscale serve --yes --https=8445 off` removed only the Ollama HTTPS route; the other five Serve Web routes compared equal before/after. Candidate source `hosts/tensor/files/etc/tensor-control/guard.nft` retains the existing 8769 guard and adds the two non-loopback rejects. It was syntax-checked with `nft -c` against the live table, temporarily deployed to `/etc/tensor-control/guard.nft` with mode 0644, and applied by the existing `tensor-control-guard.service`. Its SHA-256 is `7e47dbb66b2bb322cfc0ef69bb8b20460c53eef28ba7d2a3e85552f77f7bdd60`. After readback, the temporary nft table was deleted. The boot-enabled `tensor_control` chain held the rule during the trial; the unrelated 8769 allowlist remained intact. `inventory/deployments.json` records the candidate source but marks it **not deployed** after rollback.

**Observed checks:** From the Nexus Hermes container, TCP to Tensor 192.168.1.3:11434 and :7860 was refused; SSH :22 connected. On Tensor, loopback GET `/api/version` and WebUI `/` both returned HTTP 200 without invoking a model. Tailscale Serve 8445 was absent; the other routes were unchanged. `tensor-control-guard.service` was active/successful. Ollama subsequently reported no loaded model without an operator unload. `hermes-llama.service` stayed failed; no GPU request, service restart, queue migration, Qdrant write, PDF conversion, process kill, or model eviction was performed.

**Targeted rollback — executed after validation to avoid prolonged client interruption:**

1. On Tensor, `sudo install -o root -g root -m 0644 /var/lib/tensor-gpu-admission/guard-before.nft /etc/tensor-control/guard.nft && sudo systemctl restart tensor-control-guard.service`. Original SHA readback matched; the 8769 guard remained and the 11434/7860 reject was gone.
2. Restored only the prior Ollama Serve path with `sudo tailscale serve --bg --https=8445 http://127.0.0.1:11434`. Readback of all six Web routes matched the protected pre-change snapshot. TCP from the Nexus Hermes container to Tensor 11434, 7860 and SSH 22 all connected. The WebUI and Ollama services were not restarted; llama remained failed. This is the validated cutover rollback, not a reason to reset all Serve routes.

**Current state/next gate:** Direct clients are restored because no protected handoff worker, sleep-aware lease or guarded WebUI boundary is ready to replace them. The Git candidate rule is **not deployed**. Local loopback processes would bypass this network-input rule even during a future cutover, so unknown local activity/GPU ownership remains an admission veto. The controlled restriction can be reapplied only at a verified cutover, after rechecking live clients and backups. Qdrant writers/checkpoints were not altered. A real fail-closed Hermes policy, sleep-aware lease, worker, guarded MinerU entry point, and end-to-end inference/embed/PDF acceptance remain pending.
