# Authenticated purchase-alert intake and scheduled receipt projection

Date: 2026-11-09. Objective: ingest new purchase-alert emails as **evidence**, propose scanned-receipt matches without duplicate expenses, and run the verified receipt/item projection regularly. Nexus host and private `iragonforce/ops`; containing Git revisions own source and deployment records.

## Data boundary and backup

Local Proton Bridge IMAP `127.0.0.1:1143` is authenticated with the existing Bitwarden Secrets Manager `PROTON_BRIDGE_IMAP` credential, kept only in process memory. Its username is in root-only `/etc/nexus/secrets/finance-imap-user` (0600) and **not** in Git. The script selects All Mail read-only and uses `BODY.PEEK[]`; it does not mark mail read, move messages, or forward content. The parser accepts only exact `cibc.com` From domain, exact purchase-alert subject/body template, aligned `dkim=pass header.d=cibc.com`, a valid Message-ID and a zoned mail date. It does not store the raw body or card suffix. An email timestamp is not a purchase/posting date; a notification is not a bank transaction or receipt.

Immediately before the analytics schema change, a fresh PostgreSQL 17 custom-format dump was streamed through the existing Bitwarden-keyed GPG AES256 path without writing plaintext. Nexus `/var/backups/homelab/finance/pre-mail-ingest-2026-11-09` and Qubit `~/.local/share/finance-infrastructure/backups/pre-mail-ingest-2026-11-09` have protected encrypted copies and a matching SHA-256 manifest (0600 files, 0700 directories). `pg_restore -l` succeeded; an actual **network-isolated PostgreSQL 17 restore** of this artifact returned the pre-change **17 purchase receipts / 74 items**, and its temporary container was removed. The backup covers this analytics database, not live Proton Bridge mailbox state or all finance services. The earlier full Wealthfolio appdata restore evidence remains separate.

## Failure handling, limitations, rollback

The intake service exits nonzero on changed Message-ID payload, unknown supported template, unauthenticated sender, missing IMAP UIDVALIDITY, altered secrets or DB readback mismatch. Hourly failures are visible in the native systemd unit; no tested Telegram failure alert is attached yet. Full mailbox scanning is capped at 2,000 purchase-subject candidates and will fail closed at that boundary rather than silently omit mail; incremental polling and retention should be addressed before growth. Provenance is preserved in the source mailbox and the protected DB, with no raw message bodies in logs/Git. All candidate receipt links stay tentative and collision-aware; no bank activity or budget amount is inferred from email alone.

For a fault, disable only `finance-intake.timer` (preserve service/history), inspect the exact state and source hashes, then fix and rerun `--preview`. Targeted rollback for this stage is to remove only the newly created `transaction_email_alerts` table **after confirming it has no later consumers or reviewed links**; the pre-mail encrypted PG17 snapshot is a tested last-resort recovery source, not permission to restore over concurrent edits. Restore the exact Git-owned unit/script versions through guarded deployment if code rollback is needed. Root-only username file can be removed only after stopping intake and confirming no consumer; do not publish its contents. Backup retention and application-level recovery remain incomplete.
