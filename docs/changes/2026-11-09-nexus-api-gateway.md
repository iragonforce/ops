# Nexus API gateway inventory and read-only expansion — 2026-11-09

Objective: create the API project, enumerate Nexus Docker containers and live Kong routes, connect safe remaining read APIs to `api.blinkwired.com`, return a default domain-root response, and keep upstream/rollback credentials in Bitwarden with GitHub-backed recovery.

## Changes

- Created the Hermes desktop project `API` at `/opt/data/workspace/api`, with a 75-container (73 running) inventory and a catalog of all 69 Kong service/route objects. The snapshot maps 36 containers to Kong names/adapters and classifies the other 39 rather than publishing databases, internal UIs, agent execution, CalDAV, CA/Thread controls or non-HTTP transports blindly. No new service, scheduled job or persistent script was added.
- NPM proxy host 201 had targeted the nonexistent `homelab-api-gateway`; updated it through its authenticated API to `api-gateway:8000`. Added an exact `/` Nginx location returning a small JSON response, with the other locations unchanged. The full pre-change NPM record was encrypted and pushed to GitHub before modification.
- Added the already-vaulted Photon API token to the existing Compose expansion overlay and recovered its previously failing Kong status route. Activated six read-only API routes behind the pre-existing JWT and `api-full-read` ACL: Sonarr, Radarr, Lidarr, Prowlarr, qBittorrent and Bazarr. Existing *arr/qBittorrent credentials were reused; the verified live nested Bazarr API key was added to Bitwarden `infrastructure` as `BAZARR_API_KEY` (`2e42c538-42e7-491b-936a-b4fd013950c3`). No credential was printed or committed.
- Created a dedicated Bitwarden `infrastructure` rollback key `API_KONG_BACKUP_GPG_PASSPHRASE_V1` (`08d472d9-9c70-49de-9008-b4fd0132c9c8`). The original, intermediate and final Kong JSON were encrypted with GnuPG AES256, decrypted byte-identically and committed to private `iragonforce/backup`, branch `api-gateway-2026-11-09`, alongside non-secret Compose and recovery documentation. The plaintext JWT signing secrets were never pushed. Project Git history records the exact revisions and checksums.

## Checks and limits

- Kong 3.9.4 parsed each staged JSON. The final container is healthy with zero restarts; the live file matches the encrypted final artifact's recorded SHA-256. NPM `nginx -t` passed and its `api-gateway` upstream resolves. Through NPM HTTPS with valid TLS, root returned JSON 200; protected health returned 401 without JWT and 200 with the existing JWT; Photon, n8n, all four *arr status routes, qBittorrent version and Bazarr languages returned 200 with JWT, while Bazarr without JWT returned 401. Existing consumer ACLs and Kong global JWT were preserved.
- Public IPv4 Cloudflare returned 302 to the configured Cloudflare Access login. This does not test a completed browser login or end-to-end authorized edge-to-origin query. IPv6 was unreachable from the Hermes container. The FlareSolverr arbitrary-target POST route remains deliberately `api-expansion-pending`; its narrow GET health route was already active. Not every matched Kong service was functionally exercised. Independent owner-side Bitwarden/GitHub recovery remains unverified.
- During a Compose recreation, a disposable container's `/site` project-directory alias became a nonexistent **host** bind source, briefly restarting the gateway with a directory instead of `kong.json`. Logs identified the exact cause; using the identical host path `/opt/homelab-api` inside the tool container restored the original file mount and full health. The accidentally created empty `/site` directories were inspected, found unused and removed. The failure was not treated as a successful deployment. Future Compose tools must use an identical host-visible project path.
